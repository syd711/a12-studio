Introduction
The Helm A12 Stack is a comprehensive collection of Helm charts designed to provide an out-of-
the-box solution for deploying A12-based applications on Kubernetes.
The charts are categorized into two groups:
• Common Requirements: Charts that address the general needs of the application.
• A12 Components: Charts specific to the different A12 components.
The primary goal of the A12 Helm Stack charts is to facilitate the deployment of A12-based
applications, along with their supporting infrastructure, with minimal configuration effort. At the
same time, they offer the flexibility to adapt to specific requirements.
TIP
Always review the README.md and values.yaml files included with a chart, or use the
command helm show values chart-name to understand the configurations, default
values, and descriptions. This will help you grasp the configurations and extensions of
a Helm chart.
You can browse these files directly from the chart repository in mgm Bitbucket (for
mgm internal use) and the chart package in mgm Artifactory (for mgm internal use)
or GetA12 Artifactory (for partners).

Elementary Charts
A12 Secrets
The A12 Secrets Helm Chart consists of templates for generating secrets that are referenced by the
infrastructure charts as well as by the application charts.
Some secrets are shared by both the infrastructure and application components. For example, the
PostgreSQL secrets are used in the infrastructure chart to initialize the database and in the
application charts to connect to the database.
There are many ways to deal with secrets. You could for example
• use the helm-secrets plugin
• use the Ansible Helm module and Ansible Vault
• use the HashiCorp Vault
The helm-secrets plugin is used in this documentation, as it is the most transparent for using
encrypted secrets with Helm.
Encryption / Decryption
Secrets must be added to a repository only in an encrypted way. To encrypt your secrets with helm-
secrets plugin, you need to create or import a PGP key and create a file .sops.yaml to reference to it
for using with SOPS or helm-secrets.
creation_rules:
# Encrypt with PGP (obtain via gpg --list-secret-keys)
- pgp: '000111122223333444AAAADDDDFFFFGGGG000999'
You can also specify different secrets for different environments of your project following the
example of directory structure below.

A12 Data Services
The A12 Data Services Helm Chart supports you in deploying a server application based on Data
Services in a cluster-safe way including initialization of models and documents.
The example below shows the basic usage of the Helm chart values. For a more complete
description of all available values see the link to the repository above or look into Helm chart

Models and Documents Import
There are a few ways to support importing models and documents in your application. With this
chart, we provide a standard way for models and documents importing, which is downloading
compressed models and documents and then refer to them during the initialization phase. Using
this way, you do not have to rebuild your server images when the changes are only related to
models or adding initial documents.
Below is an example of how it could be configured in this chart. Please be aware that models and
documents resources are expected to be archived following the instruction in the Project Template.
If not, you will have to add your own commands in the download resources init container at
resourcesImport.command.
# Configuration in a12-data-services chart
resourcesImport:
enabled: true
url: "https://your-models-and-document-resource-url-here"
# Configuration in a12-secrets chart, if you need authentication for downloading
resources.
resourcesDownload:
enabled: true
username: your-username
password: your-password
We add one init container to download and extract the resources at the correct location so that
DataServices init job and application can pick them up for importing.
Authentication is also added to download models and documents from non-public resources.
You can look into the chart for more detail.
If you are not satisfied with the provided method, you can turn it off easily by setting

resourcesImport.enabled to false and supply your own method, either using init container or
container for importing models and documents.
Single Instance Deployment
To deploy a single instance of your server application based on DataServices, you can either:
• Using the approach Multi Instances Deployment with Initialization and set the replicaCount to 1
(default value).
• Don’t need cluster-safe configuration and dedicated initialization job. Models and documents
can be imported either during the initialization phase of the DataServices container or using an
init container. By choosing this way, you will have to configure the resources imported by
yourself.

enabled: true

Maintenance Mode
Maintenance mode can be used when you deploy a new release of your application and want to
perform testing of your application while displaying a user-friendly page to end user that the
application is under maintenance.
When maintenance mode is enabled, the chart deploys a separate NGINX‑based pod serving a static
maintenance page, alongside your normal application. It does not scale down or remove your
primary deployment; instead, it relies on a dedicated Ingress/Service to route traffic to the
maintenance endpoint. To enable maintenance mode for a12-client chart
helm upgrade a12-client helm-repos/a12-client --install \
-n project-x \
-f values.yaml --set global.maintenance.enabled=true
To disable it
helm upgrade a12-client helm-repos/a12-client --install \
-n <namespace> \
-f values.yaml \
--set global.maintenance.enabled=false
• Dedicated Maintenance Pod: Runs NGINX to serve your maintenance page.
• Ingress Switching: Renders a separate Ingress pointing to the maintenance Service.
• ConfigMap Flexibility: Using predefined ConfigMap for maintenance page of supplying
your awesome design.

Prometheus Metrics
You could configure A12 Data Services, A12 Content Store, and A12 Workflows (Camunda) to expose
HTTP(S) endpoints containing Prometheus formatted metrics. To do so, please use the following
values in the corresponding chart.
actuator:
enabled: true
prometheusEndpointAccess: read_only
# Add the "prometheus" endpoint here. The "health" endpoint is enabled by default
(for readiness and liveness check)
exposeEndpoints: "health,prometheus"
Metrics will be exposed on the /actuator/prometheus endpoint by default.
If you use Prometheus Operator on your cluster, the following values deploy a Service Monitor
targeting the above service endpoint. Please make sure you have the proper network policies that
allow the connection from Prometheus.

Local Cluster for Development
Tool Suggestions
For local development purposes, you might want to have your own cluster to play around with the
provided charts and examples from A12 Build and Deployment team. Furthermore, you can use
this for running your developed applications and many other components.
We have tested several tools and would suggest using minikube as a good candidate because
• Simple to set up on a local machine with good documentation
• Supports multi-platform (Linux, macOS, Windows)
• Addons with the ability to enable nginx ingress out-of-the-box
A12 stack charts can run normally on a standard minikube cluster. The speed of deployment and
running application cannot be comparable to a dedicated cluster. However, it would provide you a
minimal viable environment to quickly test your deployment script.
Tips and Tricks
Below are with some helpful notes for you to speed up your development speed as well as being
aware of some common issues that might happen during your daily work.
• Update storageClass in persistence block of all the charts to the available/desire storage class
you want to use in the cluster. If you use minikube (v1.26.1), the default storage class would be
standard.
• Enable nginx ingress addon in minikube and follow the instruction to tunnel access to your
application in the browser.

• Adjust the livenessProbe.initialDelaySeconds so that it could wait for the application to be

Migration Instructions
2026.06
8.0.0
IMPORTANT
Breaking changes in a12-infrastructure: Keycloak, PostgreSQL, and Hazelcast
removal
Keycloak: from version 7.1.x, the a12-infrastructure chart shipped a
vendored copy of the Bitnami Keycloak chart, adapted to run the official
Keycloak image (earlier versions consumed the Bitnami Keycloak chart as a
dependency). Starting with 8.0.0, Keycloak is deployed through the
upstream codecentric keycloakx chart (version 7.2.0, Keycloak 26.6.2),
consumed as a dependency. Because the configuration keys of keycloakx
differ from the previous Bitnami-style keys, all overrides under a12-
infrastructure.keycloak must be re-mapped. The A12-specific additions
(realm initialization job and Gateway API resources) are retained
unchanged.
PostgreSQL: the default PostgreSQL image is updated to version 18.4. If you
upgrade an existing PostgreSQL instance, the data directory must be
migrated to the new major version before starting the new container,
otherwise PostgreSQL will refuse to start. See the PostgreSQL upgrade
documentation.
Hazelcast: the Helm chart hazelcast is removed from the a12-infrastructure
Helm chart since it is not required in Data Services anymore. As a
consequence, the related admin secret is also removed from the a12-secrets
Helm chart.
The Keycloak state lives in the database, so no data migration is required — a working database
connection is sufficient to bring the new deployment up. If you instead want to move realm data,
export the realm from your existing Keycloak (see Keycloak: exporting a realm) and let the chart
import it through the realm initialization job configured under a12-
infrastructure.keycloak.a12.init.
